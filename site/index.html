Five small tools,
one container image.

This is a cloud-computing exercise: build a single nginx image once, then run it three different ways — alone, replicated, and as five distinct services that differ only by the content mounted into them at runtime.

Three run modes — same image every time

01

Single container

One nginx serving the page you are reading, baked into the image at build time.

host port 8080
docker compose up -d
02

Five replicas

One service scaled to five. Compose hands each replica its own host port from a range.

host ports 8081–8085
docker compose -f docker-compose.scale.yml \
  up -d --scale web=5
03

Five unique services

Five containers, one image, five read-only volume mounts. Content is the only difference.

host ports 8091–8095
docker compose -f docker-compose.unique.yml \
  up -d

The five services — mode 03

ServiceWhat it doesPortMounted from
Recipe Scaler Rescales built-in recipes to any serving count, with honest fractions. 8091 ./services/recipe
Departure Board A split-flap airport board that flips through live status changes. 8092 ./services/board
Constellations Twelve constellations on a canvas sky you can rotate through the night. 8093 ./services/sky
Bill Splitter Even splits, or itemised ones with tax and tip shared out proportionally. 8094 ./services/split
Typing Test Sixty seconds, live WPM and accuracy, and the characters you keep fluffing. 8095 ./services/typing

Why this matters. Only one image is ever built. Mode 02 proves the image is stateless enough to replicate; mode 03 proves configuration and content can be injected at run time rather than baked in. Rebuilding an image per service would be the wrong answer to the same problem.
